1.b Optimization Engine

Notation follows the GridFlow engine reference. Code variable names are given in parentheses.

Overview

Voltgrid splits the optimization into two successive steps.

Step 1 — Problem Setup assembles the LP structure: nodes are loaded, balance constraints (\(S \cdot v = 0\)) are encoded, and individual and network dispatch objectives are defined. No solver is called at this stage.

Step 2 — Cooperative Tradeoff then solves the problem in two phases. The need for two phases comes from a well-known failure mode of classic dispatch applied to networks: a single highly efficient node can monopolize all available supply and drive every other member to zero output. To prevent this, GridFlow introduces a tradeoff parameter \(\alpha \in [0,1]\) that relaxes the network dispatch constraint, giving lower-output nodes room to remain active.

Concretely:

  1. Phase 1 (LP) — run a standard dispatch to obtain the maximum achievable network dispatch rate \(\mu_c^*\).
  2. Phase 2 (QP) — fix \(\mu_c \geq \alpha \cdot \mu_c^*\) and minimize \(\sum_i \mu_i^2\), which distributes dispatch as evenly as possible across all nodes.

This approach is much faster than multi-objective alternatives and yields an optimum conceptually similar to fair-share dispatch: each node operates at its maximum rate without diminishing the output of others — hence cooperative. In the absence of additional constraints, the resulting dispatch rates are correlated with node capacity within a network, not as a prior assumption but as a direct consequence of the optimization.

Step 2 — Cooperative Tradeoff

The LP assembled in Step 1 is solved in two successive phases. Phase 2 replaces the objective in place (LP → QP) before calling the solver again — the constraint structure is not rebuilt.

NoteWhy two phases?

Phase 1 finds the theoretical maximum dispatch rate \(\mu_c^*\). Phase 2 then asks: given that the network dispatches at least at \(\alpha \cdot \mu_c^*\), what is the most equitable distribution of dispatch rates across nodes? The two-phase structure avoids solving a bilevel problem directly.

Base problem — shared by both phases

Decision variables

Variable Description
\(v^i_x\) Flow of each line in each node (all nodes combined)
\(\mu_i\)   (objective_[nd]) Individual dispatch rate — stored as a constraint, read as primal value
\(\mu_c\)   (network_objective) Network dispatch rate, linked by equality to \(\sum_i \tilde{b}_i \cdot \mu_i\)

Constraints

Constraint Formulation
Balance \(S \cdot v = 0\) for every bus in every node
Non-negative dispatch \(\mu_i \geq 0\) for every node \(i\)
Transfer flow bounds import bound \(/ B\), export bound unchanged (supply-controlled)
Capacity coupling Stoichiometric coefficient on shared bus \(= \tilde{b}_i\)
Network objective \(\mu_c = \sum_i \tilde{b}_i \cdot \mu_i\) (equality constraint)
WarningS·v = 0 is never explicit

The incidence matrix \(S\) is never built as a matrix object. It is encoded implicitly by GridCore: each bus becomes a constraint, and each line writes its incidence coefficients into that constraint via set_linear_coefficients().

Solver call

# problems.py : 78-82

min_dispatch = optimize_with_retry(net, ...) / net.scale

Output → \(\mu_c^*\) : maximum achievable network dispatch rate (min_dispatch)

TipThis is a standard LP

Phase 1 is a plain linear program. Any solver works (GLPK, CPLEX, Gurobi). The result \(\mu_c^*\) is used only as a bound in Phase 2 — it is not the final answer.

Objective

\[\min \quad \sum_i \mu_i^2\]

Minimizing the sum of squares penalizes solutions where one node monopolizes dispatch. It finds the dispatch rate distribution closest to equal sharing across nodes.

Additional constraints

\[\alpha \cdot \mu_c^* \leq \mu_c \leq \mu_c^*\]

where \(\alpha\) (fraction) is the tradeoff parameter set by the user.

Objective construction in code

# problems.py : 53-66
def regularize_l2_norm(network, min_dispatch):
    l2 = Zero
    for nd in network.nodes:
        node_obj = network.constraints["objective_" + nd]
        ex = sum(v for v in node_obj.variables if (v.ub - v.lb) > 1e-6)
        if not isinstance(ex, int):
            l2 += (network.scale * (ex**2)).expand()
    network.objective = -l2   # minimize L2 ≡ maximize -L2

Output → NetworkSolution : individual dispatch rate \(\mu_i\) per node

WarningRequires a QP-capable solver

Phase 2 introduces a quadratic objective. GLPK cannot solve it. Gurobi, CPLEX, or the hybrid solver are required.

1.c Supply Profiles and Add-ons

How supply inputs and reserve injections are incorporated as constraints on transfer flows.

Supply File Format

In the pipeline, a supply profile is passed to GridFlow as a packed artifact (zipped archive). Inside this archive, the core data is a CSV file with two essential columns:

Column Description
id Transfer line identifier (e.g. EX_pv__D_e for solar import)
flux Maximum import flow for that source (\(kW \cdot h^{-1} \cdot MVA^{-1}\))

Each row represents one source available in the grid environment. The id maps directly to a transfer line in the network model.

What is a Flow?

A flow (\(v_i\)) is the rate at which power is drawn or produced by a transfer line. In the context of a supply profile, it represents the maximum quantity of power that nodes can import per unit time and per unit of installed capacity.

The unit \(kW \cdot h^{-1} \cdot MVA^{-1}\) breaks down as:

  • \(kW\): amount of power (kilowatts)
  • \(h^{-1}\): per hour
  • \(MVA^{-1}\): normalized by total installed capacity

This normalization by \(MVA\) is key: the flow value is independent of the site’s footprint. It expresses a rate relative to the network itself, not to the external load.

The conversion from raw supply to flow is:

\[v_i = \frac{D_i \times (1 - A_i) \times 1000}{Mw_i \times B_{total}}\]

Symbol Description Unit
\(v_i\) Maximum flow available to nodes \(kW \cdot h^{-1} \cdot MVA^{-1}\)
\(D_i\) Raw supply of source \(i\) \(kW \cdot h^{-1}\)
\(A_i\) Upstream losses (before the bus) unitless
\(Mw_i\) Conversion factor of source \(i\) \(kW \cdot unit^{-1}\)
\(B_{total}\) Total installed capacity \(MVA\)

Supply as a Constraint in the Optimization

Inside cooperative_tradeoff, the supply profile is not a decision variable — it is a constraint on import flows, applied before any optimization begins (grow.py:55):

net.medium = medium[medium.index.isin(ex_ids)]

This sets an upper bound on each transfer line:

\[0 \leq v_{\text{import},i} \leq v_i\]

Nodes cannot draw more than what the supply allows. This is the operating ceiling imposed on the optimization problem.

The supply profile therefore contributes to both phases:

  • Phase 1 (LP): limits the feasible space for maximizing network dispatch
  • Phase 2 (QP): same bounds apply when redistributing flows under the tradeoff constraint

Supply as a Decision Variable (Supply Optimizer)

In supply_optimizer.py, the logic is reversed: the goal is to find which supply profile to schedule in order to reach an operating objective (e.g. maximize reserve power output).

Decision Variables

Variable Description Bounds
\(f_i\) Amount of source \(i\) (units) \([f_i^{\min},\ f_i^{\max}]\)
\(a_i\) Addition relative to current profile \([0,\ f_i^{\max} - f_i^{\text{current}}]\)
\(r_i\) Reduction relative to current profile \([0,\ f_i^{\text{current}} - f_i^{\min}]\)
\(\delta_i \in \{0,1\}\) Binary indicator: was source \(i\) modified? —

Constraints

Constraint Expression Purpose
Source balance \(f_i = f_i^{\text{current}} + a_i - r_i\) Tracks net change per source
Max sources changed \(\sum_i \delta_i \leq N\) Limits schedule complexity
Change indicator \(a_i + r_i \leq 1000 \cdot \delta_i\) Links binary to actual change
Load envelope \(\text{load}_{\min} \leq \sum_i f_i \cdot \text{kW}_i \leq \text{load}_{\max}\) Operating feasibility
FBA — balance (optional) \(\sum_r S_{m,r} \cdot v_r = 0\) for each bus \(m\) Incidence feasibility of grid operation
FBA — supply coupling (optional) \(v_{EX_i} \geq -\dfrac{\text{supply\_flux}_i}{\text{FLUX\_CONVERSION\_FACTOR}}\) Node draw cannot exceed what the supply provides
NoteFBA constraints change the nature of the problem

Without --model: the objective operates on supply flows directly — the optimizer reasons about source quantities and their power content.

With --model: the balance constraints are injected via _embed_network_model(), coupling the supply to actual grid operation. The optimizer now reasons about true network flows (e.g. reserve output as a result of node dispatch), not just supply composition.

Objective Function

\[\min \sum_i \text{penalty} \cdot (a_i + r_i) - \sum_j w_j \cdot v_j^{\text{objective}}\]

Minimize supply perturbation while maximizing the target operating flow (e.g. reserve export EX_res(e)).

def add_var_from_expression(model, name, expr, lb=None, ub=None):
    var = model.problem.Variable(name, lb=lb, ub=ub)
    const = model.problem.Constraint(
        (var - expr).expand(), lb=0, ub=0, name=name + "_equality"
    )                                    # network_objective = Σ capacity_nd × dispatch_nd
    model.add_cons_vars([var, const])
    return var

Step 2 — Cooperative Tradeoff

Main function

# problems.py : 70-100
def cooperative_tradeoff(network, min_dispatch, fraction, flows, pfba, atol, rtol):
    with network as net:
        _apply_min_dispatch(network, min_dispatch)     # optional: objective_[nd].lb = min_dispatch_nd

        # Phase 1 ─────────────────────────────────────────────────────────
        net.objective = net.scale * net.variables.network_objective
        min_dispatch = optimize_with_retry(net, ...) / net.scale

        # Phase 2 ─────────────────────────────────────────────────────────
        regularize_l2_norm(net, 0.0)
        for fr in fraction:
            net.variables.network_objective.lb = fr * min_dispatch   # dispatch floor
            net.variables.network_objective.ub = min_dispatch        # dispatch ceiling
            sol = solve(network, flows=flows, pfba=pfba, ...)
            if not pfba and sol.status != OPTIMAL:
                sol = crossover(net, sol, flows=flows)

# problems.py : 78  /  solution.py : 214-223

def optimize_with_retry(net, message):
    sol = net.optimize()           # first solver call (LP)
    if sol is None:
        network.solver.problem.reset()   # Gurobi reset on failure
        sol = net.optimize()
    return sol.objective_value
